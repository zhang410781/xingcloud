# 告警规则与通知

> 状态：当前已实现

## 1. 统一告警源

平台使用统一 `AlertSource` 管理三类来源：Prometheus、Alertmanager 和 Zabbix。告警源是规则、负责人、通知策略、聚合隔离和审计的配置边界，不依赖业务上下文。

Prometheus 告警源一对一绑定指标数据源；Alertmanager 和 Zabbix 告警源提供独立 Webhook 标识和 Bearer Token。每个启用的告警源配置一名主负责人及可选协同负责人，并可按告警级别划分责任。

## 2. 全局规则模板

内置模板与用户自定义模板使用统一状态机：草稿、待审核、已发布和已归档。所有用户可以使用已发布模板；具备配置管理权限的用户可以创建、审核、发布和归档全局模板。

模板保存 PromQL、标签维度、单位、阈值、持续时间、摘要、详细描述和证据采集配置。模板本身不绑定数据源，创建规则实例时选择 Prometheus 告警源。新实例默认禁用，需试运行成功后启用。

## 3. 规则运行

规则实例只从其告警源绑定的 Prometheus 查询，不回退到默认数据源。运行质量记录最近执行时间、耗时、错误、无数据次数、触发次数、抖动次数和最近命中对象。

“无数据”表示查询没有返回可评估样本，不代表告警触发。业务上下文可以在后续精准研判中补充日志、K8S 和变更证据，但不是规则求值前置条件。

## 4. 外部告警标准化

Alertmanager 和 Zabbix 通过来源级字段映射转换为平台统一告警字段。来源可配置稳定指纹字段；最终指纹自动包含告警源身份，避免不同来源串告警。

动态原因、当前值和时间戳不作为长期状态告警身份。Waiting 告警默认按集群、namespace、Pod、container 和 UID 合并，`ErrImagePull` 与 `ImagePullBackOff` 的变化更新时间线和证据，不产生新的活动告警。

## 5. 通知资源与策略

通知渠道、接收人和接收组是全局复用资源。接收人保存个人联系方式及渠道偏好；告警源负责人路由会同时校验负责级别、联系方式和个人偏好。

每条通知策略只属于一个告警源。策略通过结构化路由表达：

- Info、Warning、Critical 分级。
- 立即通知或未认领升级。
- 固定群、告警源负责人、指定接收组或资源负责人。
- 飞书、企微、钉钉、邮件、短信和语音渠道。
- 分组等待、同组间隔、重复间隔、静默和抑制。

不同告警源可以把同一等级发送到不同飞书群；同一告警源也可以按等级选择不同群。未认领达到等待时间后可提升告警等级并通过语音联系负责人。

## 6. 通知生命周期

1. 告警触发后按当前告警源策略发送首次通知。
2. 精准研判完成后，仅沿用本活动周期首次实际送达的策略与渠道。
3. 告警恢复后按相同来源策略发送恢复通知。
4. 恢复后再次触发进入新活动周期并重新研判。

研判继承静默、屏蔽、抑制、聚合和风暴降噪结果，不作为独立告警绕过策略发送。

## 7. 用户界面

`可观测性 / 告警规则` 使用告警源工作台：左侧选择来源，右侧按概览、负责人、规则或字段映射、通知策略和测试组织操作。跨页面导航只由平台左侧菜单承担，不在页面内重复显示第二套可观测性菜单。

详细配置步骤见[告警源、规则与通知配置使用手册](../告警源规则与通知配置使用手册.md)。
