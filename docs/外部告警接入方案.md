# 外部告警接入方案 B — 落地设计文档

> 实施状态：已在当前代码基线落地。部署时需执行数据库迁移、配置 Webhook Token，并确保告警分析 Worker 正常运行。

## 1. 概述

### 1.1 目标

被动接收 Zabbix / Alertmanager 等外部系统的告警推送，在不依赖 Prometheus、ClickHouse 等基础设施数据源的条件下，完成告警入库、轻量 LLM 研判、告警生命周期管理（升级/抑制/降噪/通知）的完整闭环。

### 1.2 适用范围

- **Zabbix**：通过 Action → Webhook 推送告警（含 Shell 脚本判警结果）
- **Alertmanager**：原生 Webhook 推送
- **后续扩展**：支持额外来源时只需在 `alert_ingest.py` 中增加标准化函数

### 1.3 非目标

- 不替代 Zabbix 侧 Shell 脚本的判警逻辑
- 不将 Zabbix 作为 Prometheus 替代品进行指标查询
- 不建设轮询 Zabbix API 拉取指标数据的能力（可在后续阶段独立实现）

## 2. 术语

| 术语 | 说明 |
|------|------|
| `normalized dict` | `upsert_alert()` 接受的标准化告警字典 |
| `fingerprint` | 告警指纹，用于去重和合并 |
| Webhook Token | 请求头 `X-Webhook-Token`，防止未授权调用 |
| 轻量研判 | 跳过证据收集，直接基于告警文本调 LLM 的分析路径 |

## 3. 系统架构

### 3.1 整体流

```
┌──────────────┐    ┌──────────────┐
│  Zabbix     │    │ Alertmanager │
│  Action     │    │  Webhook     │
│  Webhook    │    │              │
└──────┬───────┘    └──────┬───────┘
       │ POST              │ POST
       ▼                   ▼
┌─────────────────────────────────────────────┐
│          alert_ingest 端点                   │
│  POST /api/ops/alerts/ingest/              │
│                                              │
│  1. X-Webhook-Token 鉴权                    │
│  2. detect_source() 自动识别来源             │
│  3. normalizer 标准化 → normalized dict      │
│  4. upsert_alert() → 入库/去重/指纹合并      │
│  5. enqueue_lightweight_analysis() → 排队研判 │
│  6. apply_escalation_policy() → 升级检查     │
│  7. 首次创建时触发 fire 通知                  │
└────────────────────┬────────────────────────┘
                     │
                     ▼
┌────────────────────────────────────────┐
│      分析调度器 (已有，无需修改)         │
│  python manage.py run_alert_analysis_worker │
│  run_due_alert_analyses()              │
│    → claim_due_analysis()              │
│    → 根据 source_mode 分流              │
└────────────────────┬───────────────────┘
                     │
          ┌──────────┴──────────┐
          ▼                     ▼
┌─────────────────┐    ┌────────────────────┐
│ 标准分析路径     │    │ 轻量分析路径        │
│ execute_alert_  │    │ execute_lightweight_│
│ analysis()      │    │ alert_analysis()    │
│                 │    │                     │
│ 采集 Prometheus │    │ 不采集基础设施证据   │
│ ClickHouse K8s  │    │ 直接基于 raw_payload │
│ 变更等证据       │    │ + alert 文本调 LLM  │
│ → LLM 综合研判   │    │ → 文本级研判        │
│ → 置信度 ≤0.95  │    │ → 置信度上限 0.5   │
└─────────────────┘    └────────────────────┘
                              │
                              ▼
                     ┌────────────────────┐
                     │ 研判完成             │
                     │ 结果回写 alert      │
                     │ dispatch_analysis   │
                     │ 通知                │
                     └────────────────────┘
```

### 3.2 告警生命周期（全量保留）

```
Webhook 接入 → Active → 确认/认领/屏蔽/升级 → Resolved → Closed
                  ↑                                    │
                  └──────── 重新触发 Reopen ────────────┘
```

所有通知策略匹配、抑制规则、聚合维度、重复间隔、升级步骤**均不受轻量分析路径影响**。

`run_ops_scheduler` 会周期扫描仍处于 Active 的 Zabbix/Alertmanager 告警并执行到期升级，因此升级不依赖外部系统重复推送。

## 4. 详细设计

### 4.1 模型变更

**文件**: `backend/ops/models.py`

`Alert.SOURCE_TYPE_CHOICES` 扩充：

```python
SOURCE_TYPE_CHOICES = [
    (Alert.SOURCE_PLATFORM, '平台告警规则'),
    ('zabbix', 'Zabbix'),
    ('alertmanager', 'Alertmanager'),
]
```

该 `choices` 变更通过 `ops/0096_alter_alert_source_type.py` 迁移固化，部署时必须执行 `python manage.py migrate`。

### 4.2 格式适配器

**文件**: `backend/ops/alert_ingest.py`（新文件）

职责：
- `detect_source(payload)` → `str`：根据 payload 字段特征识别来源
- `normalize_zabbix(payload)` → `dict`：将 Zabbix Webhook payload 转为 `normalized dict`
- `normalize_alertmanager(payload)` → `dict`：将 Alertmanager Webhook payload 转为 `normalized dict`

#### 4.2.1 来源识别逻辑

```python
def detect_source(payload):
    if 'event_id' in payload or 'trigger_id' in payload:
        return 'zabbix'
    if 'status' in payload and 'alerts' in payload:
        return 'alertmanager'
    return 'unknown'
```

#### 4.2.2 Zabbix 字段映射表

| normalized 字段 | Zabbix payload 源字段 | 说明 |
|----------------|----------------------|------|
| `title` | `subject` / `trigger_name` | 告警标题 |
| `message` | `message` / `trigger_description` | 告警描述，脚本输出也在此 |
| `level` | `severity` → map | `information→info`, `warning→warning`, `average→warning`, `high→critical`, `disaster→critical` |
| `source` | 固定 `'zabbix'` | 来源标识 |
| `source_type` | 固定 `'zabbix'` | 来源类型 |
| `external_id` | `event_id` | 外部 ID |
| `fingerprint` | `zabbix:{trigger_id}:{host_name}` | 指纹，用于去重 |
| `resource` | `host_name` | 资源标识 |
| `resource_type` | 固定 `'host'` | 资源类型 |
| `environment` | `environment` | 环境标签 |
| `service` | `service` | 服务标签 |
| `labels` | zabbix_host/trigger_id/event_id/severity | 结构化标签 |
| `raw_payload` | 全量 payload | 原始载荷，LLM 分析使用 |
| `starts_at` | `timestamp` | 触发时间 |
| `status` | `event_status` / `problem_status` / `status` | `PROBLEM` 映射为 `active`，`RESOLVED` / `OK` / `RECOVERY` 映射为 `resolved` |

#### 4.2.3 Alertmanager 字段映射表

| normalized 字段 | Alertmanager payload 源字段 |
|----------------|---------------------------|
| `title` | `alerts[0].annotations.summary` |
| `message` | `alerts[0].annotations.description` |
| `level` | `alerts[0].labels.severity` → map |
| `source` | 固定 `'alertmanager'` |
| `source_type` | 固定 `'alertmanager'` |
| `external_id` | `alerts[0].fingerprint` |
| `fingerprint` | `alertmanager:{fingerprint}` |
| `resource` | `labels.instance` / `labels.pod` / `labels.host` |
| `resource_type` | `labels.resource_type` |
| `environment` | `labels.environment` |
| `cluster` | `labels.cluster` |
| `namespace` | `labels.namespace` |
| `service` | `labels.service` / `labels.job` |
| `metric_name` | `labels.__name__` |
| `labels` | 全量 labels + alertmanager 元信息 |
| `annotations` | 全量 annotations |
| `raw_payload` | 全量 payload |
| `starts_at` | `alerts[0].startsAt` |
| `ends_at` | `alerts[0].endsAt`（resolved 时） |
| `status` | `alerts[0].status` → `firing→active`, `resolved→resolved` |

### 4.3 API 端点

#### `POST /api/ops/alerts/ingest/`

平台同时保留 `/api/alerts/ingest/` 兼容地址；外部系统建议统一使用上面的 `/api/ops/alerts/ingest/`。

**请求头**:
```
X-Webhook-Token: your-configured-token
Content-Type: application/json
```

**请求体**: Zabbix 或 Alertmanager 标准 Webhook payload

**响应**:
```json
{
    "id": 42,
    "created": true,
    "fingerprint": "zabbix:12345:web-server-01",
    "occurrence_count": 1
}
```

Alertmanager 一次推送多条 `alerts` 时会逐条标准化和入库，响应额外包含 `count` 与 `results` 数组；不会只处理第一条告警。

- `created: true` — 新告警
- `created: false` — 已有告警更新（occurrence_count 递增）

**错误响应**:
- `401` — Webhook Token 不匹配
- `400` — 无法识别的来源或空 payload
- `413` — 请求体超过 `ALERT_INGEST_MAX_BODY_BYTES`
- `429` — 同一 Token 每分钟请求数超过 `ALERT_INGEST_RATE_LIMIT`
- `503` — 服务端未配置任何 Webhook Token

### 4.4 轻量研判核心

**文件**: `backend/ops/alert_analysis.py`

#### 4.4.1 `enqueue_lightweight_analysis(alert, requested_by='webhook')`

- 仅对 `STATUS_ACTIVE` 告警排队
- 已有 `PENDING` / `RUNNING` 分析时复用
- `evidence.source_mode = 'webhook_text_only'` 作为分流标记

#### 4.4.2 `execute_lightweight_alert_analysis(analysis)`

执行步骤：

1. **构造证据包**：只包含 `alert` 元信息（title, message, labels, raw_payload）和一条诊断说明 "外部 Webhook 告警，无基础设施证据源"
2. **跳过证据收集**：不调 `collect_alert_evidence()`，不访问 Prometheus / ClickHouse / K8s API
3. **无确定性候选**：`_deterministic_candidates()` 返回空列表（没有日志/K8s 样本可以模式匹配）
4. **直接调 LLM**：通过 `_llm_synthesis(evidence, candidates=[])` 让模型基于告警文本做知识推理
5. **置信度上限 0.5**：纯文本分析不高于 50%
6. **结果回写**：写入 `AlertAnalysis` + 同步到 `Alert.root_cause` / `Alert.suggestion` / `Alert.raw_payload.ai_analysis`
7. **通知分发**：调用 `dispatch_alert_notifications(alert, action='analysis')`

#### 4.4.3 调度器分流

在 `run_due_alert_analyses()` 的消费循环中，根据 `evidence.source_mode` 选择执行路径：

```python
evidence = analysis.evidence or {}
if evidence.get('source_mode') == 'webhook_text_only':
    execute_lightweight_alert_analysis(analysis)
else:
    execute_alert_analysis(analysis)
```

`run_alert_analysis_worker` 继续通过 `run_due_alert_analyses()` 自动分流。`run_ops_scheduler` 除处理研判队列外，还会调用 `run_due_external_alert_escalations()` 执行外部告警的到期升级。

### 4.5 配置项

**文件**: `backend/xing_cloud/settings.py`

```python
WEBHOOK_TOKENS = {'default': os.environ.get('WEBHOOK_TOKEN', '')}
ALERT_INGEST_RATE_LIMIT = 120
ALERT_INGEST_MAX_BODY_BYTES = 1_048_576
```

生产环境必须从环境变量或 `config.json` 的 `alert_ingest` 段读取，不得硬编码。支持的环境变量为 `WEBHOOK_TOKEN`（兼容 `ALERT_WEBHOOK_TOKEN`）、`ALERT_INGEST_RATE_LIMIT` 和 `ALERT_INGEST_MAX_BODY_BYTES`。

Kubernetes 环境可将 Token 合并到现有 Secret 后滚动重启应用：

```bash
kubectl -n xing-cloud patch secret xing-cloud-secret \
  --type merge \
  -p '{"stringData":{"WEBHOOK_TOKEN":"<replace-with-generated-token>"}}'
kubectl -n xing-cloud rollout restart deployment/xing-cloud-app
```

通知策略可使用 `source_type == zabbix` 或 `source_type == alertmanager` 作为匹配条件。外部告警没有平台 `AlertRule`，但仍会经过通知策略的聚合、静默、抑制、升级、恢复与研判通知开关。

## 6. Zabbix 侧配置指南

### 6.1 创建 Webhook 介质类型

Zabbix → 管理 → 报警媒介类型 → 创建

- **类型**: Webhook
- **名称**: Xing-Cloud Webhook
- **参数**:
  - `URL`: `http://<xing-cloud-host>/api/ops/alerts/ingest/`
  - `Method`: `POST`
  - `Content-Type`: `application/json`
  - `Header`: `X-Webhook-Token: your-configured-token`

### 6.2 消息模板

```
{
    "event_id": "{EVENT.ID}",
    "trigger_id": "{TRIGGER.ID}",
    "trigger_name": "{TRIGGER.NAME}",
    "severity": "{EVENT.SEVERITY}",
    "host_name": "{HOST.NAME}",
    "subject": "{ALERT.SUBJECT}",
    "message": "{ALERT.MESSAGE}",
    "timestamp": "{EVENT.DATE} {EVENT.TIME}",
    "event_status": "{EVENT.STATUS}",
    "script_output": "{TRIGGER.EXPRESSION}",
    "environment": "",
    "service": ""
}
```

其中 `script_output` 字段会携带 Shell 脚本判警的输出全文，供轻量研判分析。

### 6.3 创建 Action

Zabbix → 配置 → 动作 → Trigger actions → 创建

- **条件**: 根据需要过滤（如特定主机组、触发器严重级别）
- **操作**: 发送到 Xing-Cloud Webhook 介质类型

## 8. 风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| Webhook Token 泄露 | 未授权告警写入 | 从环境变量读取，支持轮换；可加 IP 白名单 |
| Zabbix 告警风暴 | 短时间大量告警 | 复用已有 `storm_threshold` 机制，在 `alert_ingest` 端点加限速 |
| 轻量研判置信度低 | 分析结果可能不准确 | 置信度上限 0.5 已在代码硬限制；后续可加 Prometheus 数据源后无缝切换标准分析 |
| Shell 脚本输出过长 | LLM context 超出限制 | `raw_payload` 传给 LLM 时截取前面 24000 字符（已有 `_llm_synthesis` 中的截断逻辑） |
| 调度器未运行 | 分析一直 PENDING | 补充文档要求部署时启动 `run_alert_analysis_worker`；端点返回时已提示用户检查调度器状态 |

| 阶段 | 能力 | 依赖 |
