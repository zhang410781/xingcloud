# 告警源、规则与通知配置使用手册

> 状态：当前已实现
> 适用页面：`可观测性 / 告警规则`
> 配置原则：告警配置以告警源为作用域，不依赖业务上下文。

## 1. 配置对象

| 对象 | 用途 | 作用域 |
| --- | --- | --- |
| 告警源 | 表示一套 Prometheus、Alertmanager 或 Zabbix 来源 | 全局唯一 |
| 告警源负责人 | 指定主负责人、协同负责人及其负责级别 | 单个告警源 |
| 全局规则模板 | 保存可复用 PromQL、阈值、文案和证据配置 | 全平台 |
| 规则实例 | 在某个 Prometheus 告警源上执行模板 | 单个告警源 |
| 通知渠道 | 飞书群机器人、企微、钉钉、邮件、短信或语音网关 | 全平台复用 |
| 接收人/接收组 | 保存个人联系方式、渠道偏好和人员组合 | 全平台复用 |
| 通知策略 | 选择告警级别、触发阶段、渠道和接收对象 | 单个告警源 |

业务上下文仍可作为精准研判的补充证据范围，但不是创建告警源、规则和通知策略的前置条件。

## 2. 新增告警源

进入 `可观测性 / 告警规则`，点击“新增告警源”。

### Prometheus

1. 类型选择 `Prometheus`。
2. 选择已登记且启用的 Prometheus 指标数据源。
3. 选择一名主负责人，可增加多名协同负责人。
4. 设置负责人处理的告警级别。
5. 保存后进入“告警规则”，从已发布模板创建规则实例。
6. 先执行试运行，确认查询成功后再启用规则。

同一 Prometheus 指标数据源只能绑定一个告警源。规则执行时只使用该告警源绑定的数据源，不回退到默认数据源。

### Alertmanager

1. 类型选择 `Alertmanager`。
2. 配置主负责人和协同负责人。
3. 保存后立即记录页面返回的 Token，Token 只显示一次。
4. 在 Alertmanager 的 `webhook_configs` 中配置页面显示的 URL。
5. 使用 `Authorization: Bearer <TOKEN>` 发送请求。

### Zabbix

1. 类型选择 `Zabbix`。
2. 配置负责人并保存 Token。
3. 在 Zabbix Media Type 中使用 HTTP POST 发送 JSON。
4. 请求头使用 `Authorization: Bearer <TOKEN>`。
5. 至少发送事件状态、触发器 ID、主机标识、标题、级别和时间。

## 3. 负责人和个人渠道

每个启用的告警源必须有且只能有一名启用的主负责人。协同负责人可配置多名。

接收人在“通知资源”中维护：

- 手机号：用于短信和语音。
- 邮箱：用于邮件。
- 飞书、企微、钉钉用户 ID：用于支持个人消息的渠道。
- 个人渠道偏好：限制允许发送给该接收人的渠道。

路由选择“告警源负责人”时，平台只选择同时满足以下条件的接收人：

- 是当前告警源的启用负责人。
- 负责人配置包含当前告警级别。
- 接收人已启用。
- 目标通知类型符合个人渠道偏好并存在对应联系方式。

## 4. 全局规则模板

模板状态为：

```text
草稿 -> 待审核 -> 已发布 -> 已归档
```

- 草稿：创建人或有配置权限的用户可编辑。
- 待审核：等待有发布权限的用户确认。
- 已发布：所有有告警配置查看权限的用户都可以用于创建规则实例。
- 已归档：不能创建新实例，已有实例不受影响。

自定义模板需要填写名称、唯一编码、分类、PromQL、触发条件、默认级别、摘要模板和详细描述。内置模板和用户发布模板使用相同的实例化流程。

## 5. Prometheus 规则实例

规则实例始终绑定一个 Prometheus 告警源，包含：

- PromQL 和指标标签。
- Info、Warning、Critical 级别及阈值。
- 执行周期与持续时间。
- 通知文案和证据采集配置。
- 启用状态与运行质量。

“无数据次数”表示规则查询没有返回可评估时序，不代表触发了相同次数的告警。应检查指标名、标签、Exporter、告警源绑定的数据源及 PromQL 时间窗口。

## 6. 外部字段映射与指纹

Alertmanager 和 Zabbix 在“字段映射”中配置标准字段与来源字段的对应关系。映射采用 JSON 对象，例如：

```json
{
  "resource": "labels.instance",
  "service": "labels.service",
  "labels.product": "labels.product_name"
}
```

指纹字段决定哪些事件属于同一告警活动周期。推荐配置：

| 来源 | 推荐字段 |
| --- | --- |
| Alertmanager Pod | `alertname, cluster, namespace, pod, container, uid` |
| Alertmanager 节点 | `alertname, cluster, instance` |
| Zabbix | `trigger_id, zabbix_host` |

不要把 `reason`、当前值、时间戳或事件 ID 放入长期状态告警的指纹。以 Waiting 告警为例，`ErrImagePull` 和 `ImagePullBackOff` 是同一 Pod 的动态原因，原因变化应更新同一告警，而不是产生“恢复 + 新触发”。告警源 ID会自动加入最终指纹，不同来源不会串告警。

## 7. 分级通知路由

每条通知策略只属于一个告警源。策略内可以配置多条结构化路由：

| 字段 | 说明 |
| --- | --- |
| 级别 | Info、Warning 或 Critical |
| 触发 | 立即通知或未认领升级 |
| 等待时间 | 未认领升级生效前等待的分钟数 |
| 渠道 | 固定飞书群、邮件、短信、语音等通知渠道 |
| 接收对象 | 固定渠道、告警源负责人、指定接收组或资源负责人 |
| 升级级别 | 未认领后可将 Warning 提升为 Critical |

同一负责人管理多个告警源时，可在每个告警源的策略中选择不同飞书群。一个告警源也可以将 Warning 发到业务群，将 Critical 发到应急群。

典型配置：

| 告警级别 | 触发 | 渠道 | 接收对象 |
| --- | --- | --- | --- |
| Warning | 立即 | 产品 A 飞书群 | 固定渠道 |
| Critical | 立即 | 产品 A 应急群 | 固定渠道 |
| Warning | 未认领 5 分钟 | 语音网关 | 告警源负责人 |

## 8. 聚合、静默、抑制和研判

- 聚合：由 `group_by`、首次等待、同组间隔和重复间隔控制。
- 静默：命中静默时段或人工屏蔽后不发送通知。
- 抑制：高等级同对象告警可抑制低等级告警。
- 风暴降噪：同组大量告警只选择代表告警通知，其余保留时间线。
- 精准研判：研判结果跟随本活动周期首次实际送达的告警渠道。

如果首次告警被静默、抑制、聚合或没有匹配策略，研判仍可入库，但不会绕过告警降噪单独发送。恢复后再次触发属于新的活动周期，会重新研判。

## 9. 测试与验收

### Prometheus

1. 规则试运行返回查询成功。
2. 确认标签中存在用于资源识别和通知分组的字段。
3. 启用规则后观察最近评估时间和运行质量。

### Alertmanager/Zabbix

1. 在“测试”中粘贴样例 JSON。
2. 确认标准化后的标题、级别、资源、状态和指纹。
3. 从来源系统发送测试告警。
4. 检查告警源最近接收时间、成功/拒绝计数和接入日志。

### 通知

1. 确认渠道自身测试成功。
2. 确认告警级别存在立即通知路由。
3. 确认固定群机器人或负责人联系方式有效。
4. 验证首次通知、研判通知、恢复通知顺序。
5. 验证未认领达到等待时间后才执行语音升级。

## 10. 常见问题

### 告警已进入平台但没有通知

依次检查：告警源通知开关、策略启用状态、级别路由、静默、抑制、聚合间隔、渠道状态、接收人偏好和通知回执。

### 研判完成但没有独立通知

检查本活动周期的首次告警是否实际发送，以及策略是否开启研判通知。研判不会绕过静默、抑制和风暴降噪。

### 未认领升级没有打电话

检查告警仍为 Active、无人认领/确认、等待时间已到、升级路由使用语音渠道、目标负责人包含升级后的通知级别且配置了手机号和语音偏好。

### 外部告警反复恢复和触发

对比两个事件的指纹字段，删除 `reason`、值和时间等动态字段，保留稳定资源身份。Pod 告警优先包含 UID，避免同名新 Pod 继承旧告警。

## 11. 权限与审计

- 查看告警配置：`ops.alert.config.view`。
- 管理告警配置：`ops.alert.config.manage`。
- 查看告警：`ops.alert.view`。
- 执行认领、屏蔽和人工通知：使用对应的告警操作权限。

告警源、负责人、模板、规则、策略和渠道变更进入平台审计；Token 和渠道密钥不会在列表接口中明文返回。

## 12. 本次升级说明

统一告警源结构不兼容旧的规则实例、外部接入源、通知策略和告警历史。本次迁移会清理这些旧数据，再创建新的告警源配置；通知渠道、接收人、接收组和资源负责人资料会保留。

升级前应导出仍需参考的旧配置和历史告警。迁移完成后，按以下顺序重新配置：告警源、负责人、全局模板/规则实例、分级通知路由、测试告警。数据清理迁移不自动恢复旧记录，回滚代码前必须先恢复升级前数据库备份。
